# Checkpoint 1 — testing what you've learned from the London/West Mercia project

Two exercises, meant to be done in this order:

1. **`spot_the_bug.ipynb`** — a notebook that mirrors your existing London
   pipeline (`notebooks/london/02-04`), using the same `src/` helpers and
   real project data. Four cells have been deliberately broken. Each
   broken cell still has a markdown note above it describing what it's
   *supposed* to do — your job is to run it, notice the output doesn't
   match the claim, work out why, and fix the code.
2. **`questions.md`** — ten "explain the decision" questions about choices
   made across the whole project. No code, just reasoning, in your own
   words.

## How to use these

Given how you described your learning style — study, then practice, then
tinker to problem-solve, then test — treat this as the "test" step, which
means:

- **Don't open `answers.md` first.** It exists so you can check yourself
  *after* attempting, not as a reference to work from.
- For the buggy notebook, genuinely try to find each bug by reading the
  code and re-reasoning about what it does, before rerunning it repeatedly
  hoping the error message tells you everything. The debugging *process*
  is most of the point.
- If you get stuck on a bug for a while (more than ~15-20 min with no
  progress), that's useful signal, not failure — note which one it was
  and we can talk through it together rather than you burning an hour
  stuck.
- For the questions, answer from memory/understanding first. If you
  genuinely can't answer one at all, that's worth flagging too — it might
  mean that concept needs a re-study pass, not just a re-test.

## When you're done

Let me know how it went — which bugs took longest, which questions felt
shaky — and we'll use that to decide whether to move straight into the
next learning tier (scale & tooling, as discussed) or spend more time
here first.
